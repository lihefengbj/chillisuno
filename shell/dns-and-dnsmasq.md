# DNS 是什么？dnsmasq 又是什么？一篇讲清它们的关系

访问网站时，我们输入的是 `example.com` 这样的域名，网络通信最终却要找到对应的 IP 地址。负责在域名与网络资源之间“查目录”的，是 DNS。

而在一台 Linux 服务器或家用路由器上，你可能还会看到一个叫 `dnsmasq` 的进程。它是不是 DNS？它和上游 DNS 服务器有什么区别？本文从一次查询的路径讲起。

## 一、DNS 是什么

DNS 是 Domain Name System 的缩写，中文通常叫“域名系统”。它不是单独的一台服务器，而是一套分布式的命名系统和查询协议，用来查询域名对应的各种记录。

最常见的用途是把域名解析为 IP 地址：

- **A 记录**：域名对应 IPv4 地址。
- **AAAA 记录**：域名对应 IPv6 地址。
- **CNAME 记录**：域名指向另一个域名。
- **MX 记录**：指定接收邮件的服务器。
- **TXT 记录**：保存文本信息，常用于域名验证和邮件安全策略。
- **NS 记录**：指出某个域名区域由哪些 DNS 服务器负责。

因此，DNS 不只是“域名转 IP”，更像一套全球分布式的目录服务。它没有一个保存所有域名信息的中央数据库，而是按域名层级分工管理。

## 二、一次 DNS 查询大致经历什么

以查询 `www.example.com` 为例，常见流程可以简化成这样：

```text
应用程序
   ↓
操作系统的解析器
   ↓
本机配置的递归 DNS 解析器
   ↓（若缓存中没有结果）
根 DNS → .com 顶级域 DNS → example.com 权威 DNS
   ↓
返回查询结果，并按规则缓存
```

应用程序通常先把查询交给操作系统。系统可能先检查本机 hosts 文件或缓存；需要向外查询时，再把请求交给配置好的递归解析器。

递归解析器如果已经缓存了有效答案，就可以直接返回。如果没有，它会沿着 DNS 层级继续查询：根服务器告诉它下一步该找哪个顶级域服务器，顶级域服务器再指向负责目标域名的权威服务器，最后由权威服务器返回记录。

缓存可以减少重复查询，但缓存不是永久的：DNS 记录通常带有 TTL（生存时间），过期后需要重新查询。

要区分两个角色：

- **递归解析器**：替客户端把查询过程跑完，再返回最终答案。
- **权威 DNS 服务器**：保存并回答自己负责的域名区域中的记录。

它们都参与 DNS 查询，但职责不同。DNS 的基本概念与客户端、名称服务器之间的查询机制，定义在 IETF 的 RFC 1034 和 RFC 1035 中。

## 三、dnsmasq 是什么

`dnsmasq` 是一个轻量级网络服务程序。它可以提供 DNS 转发与缓存，也可以配合 DHCP 为局域网设备分配地址、识别设备名称；还支持 TFTP、PXE 等网络启动相关功能。

在 DNS 场景里，dnsmasq 常见的工作方式是：

1. 在本机或局域网地址上监听 DNS 请求，通常使用 53 端口。
2. 对本地配置、hosts 文件、DHCP 租约或缓存中已有的信息直接应答。
3. 对需要外部查询的请求，转发给配置好的上游递归 DNS。
4. 收到结果后返回给客户端，并按规则缓存。

可以把 dnsmasq 理解成客户端附近的“接待台”或“缓存转发站”：它接收本机或局域网设备的请求，再根据情况本地回答或转交给上游 DNS。

需要注意，**DNS 是一套系统和协议，dnsmasq 是实现部分 DNS 服务功能的软件**。二者不是同一层面的概念。dnsmasq 通常不是全球域名信息的来源，也不等于公共 DNS 服务商提供的递归解析服务。

## 四、DHCP 是什么

DHCP 是 Dynamic Host Configuration Protocol 的缩写，中文叫“动态主机配置协议”。它让设备接入网络时，可以自动取得 IP 地址以及其他网络配置，而不必逐台手动设置。

DHCPv4 最常见的分配过程通常概括为 **DORA**：

1. **Discover**：客户端广播“网络里有 DHCP 服务器吗？”
2. **Offer**：DHCP 服务器提供一个可用地址和配置。
3. **Request**：客户端请求使用其中一个配置。
4. **Acknowledge**：服务器确认分配，客户端开始使用。

DHCP 提供的配置通常包括 IP 地址、子网掩码、默认网关、DNS 服务器地址和租约时间。地址一般按租约分配：客户端需要在租约到期前续租；租约过期且未续上时，地址可以回收到地址池供其他设备使用。DHCP 也可以按客户端标识配置地址保留，让特定设备通常拿到固定地址。

要把 DHCP 和 DNS 区分开：**DHCP 负责告诉设备“网络参数是什么”，DNS 负责按域名查询记录。** DHCP 可以把 DNS 服务器的 IP 地址告知客户端，但它本身不负责把网站域名解析成 IP。

本文的 DORA 与地址池例子针对 DHCPv4。IPv6 网络还可能结合 DHCPv6、SLAAC 和路由器通告（RA）分发配置，不能把 IPv4 的所有配置方式直接套用到 IPv6。

## 五、DHCP 怎样把客户端接入 DNS

dnsmasq 可以同时承担局域网的 DHCP 服务和 DNS 缓存/转发服务。设备先通过 DHCP 获取网络参数；如果 DHCP 告诉设备 DNS 服务器是路由器或 dnsmasq 所在机器，设备之后的域名查询就会发给 dnsmasq。dnsmasq 还可以利用 DHCP 租约中的主机名回答局域网内的本地主机名查询。

```text
设备接入网络
   ↓ DHCP：获取 IP、网关、DNS 地址和租约
设备把 DNS 请求发给配置的解析器（例如 dnsmasq）
   ↓
dnsmasq 查询本地记录或缓存；必要时转发到上游递归 DNS
   ↓
上游 DNS 必要时继续查询权威 DNS
```

简单说，DHCP 可以把客户端“指引”到 dnsmasq；dnsmasq 则可以同时给客户端分配网络参数、接收 DNS 查询，并把 DHCP 客户端名称与本地 DNS 应答关联起来。DHCP 服务器和 DNS 服务器不一定是同一台设备，也不一定必须由 dnsmasq 同时承担。

下面是一个简化的 dnsmasq DHCPv4 配置示意。示例使用文档专用网段 `192.0.2.0/24`，实际部署时应替换为自己的局域网地址；网关/DNS 地址应是客户端可访问、且 dnsmasq 正在监听的局域网地址：

```ini
# 动态地址池：起始地址、结束地址、租约时长
dhcp-range=192.0.2.100,192.0.2.200,12h

# 告知客户端默认网关和 DNS 服务器
dhcp-option=option:router,192.0.2.1
dhcp-option=option:dns-server,192.0.2.1

# 为指定客户端保留地址，并登记一个局域网主机名
dhcp-host=00:11:22:33:44:55,192.0.2.20,printer
```

局域网中通常应明确由哪台设备提供 DHCP。若多个未协调的 DHCP 服务器同时给同一网段分配地址，客户端可能拿到不同的网关或 DNS 配置，甚至出现地址冲突。DHCP 广播通常只在本地网段传播；跨网段服务一般需要网络设备配置 DHCP relay。

## 六、DNS 查询与 dnsmasq 的关系

如果一台服务器上的 `/etc/resolv.conf` 配置了：

```text
nameserver 127.0.0.1
```

这表示系统把 DNS 请求交给本机的 `127.0.0.1`。如果 dnsmasq 正在本机回环地址的 53 端口监听，那么它就可能是本机的 DNS 接收端。它再把外部域名请求转发到上游递归 DNS。

完整链路可以表示为：

```text
应用 → 操作系统解析器 → 本机 dnsmasq → 上游递归 DNS → 权威 DNS（必要时）
```

其中：

- **DNS** 规定了域名查询、响应以及记录的格式和规则。
- **dnsmasq** 接收并处理 DNS 请求，可提供本地答案、缓存和转发。
- **上游递归 DNS** 负责继续查询互联网 DNS 层级，并返回最终答案。

上游 DNS 可以是企业内网 DNS、路由器、运营商 DNS，或其他递归解析服务。具体应根据网络环境配置。

## 七、`dig` 怎么用

`dig` 是 DNS 查询与排障工具。它会直接向 DNS 服务器发送查询，并打印响应内容，适合比较“系统当前配置的解析器”“本机 dnsmasq”和“上游 DNS”是否表现一致。

基本格式是：

```bash
dig [@DNS服务器] 域名 [记录类型] [选项]
```

- `@DNS服务器`：指定要查询的 DNS 服务器；省略时，`dig` 通常使用 `/etc/resolv.conf` 中配置的服务器。
- `域名`：要查询的名字，例如 `example.com`。
- `记录类型`：例如 `A`、`AAAA`、`MX`、`TXT`；省略时通常查询 A 记录。
- `选项`：控制输出、超时、重试次数或查询方式。

常用示例：

```bash
# 使用系统配置的 DNS 查询 A 记录
dig example.com

# 明确查询本机 dnsmasq
dig @127.0.0.1 example.com A

# 绕过本机 dnsmasq，直接问指定的上游 DNS
# 192.0.2.53 是文档示例地址，替换成实际可用的上游 DNS
dig @192.0.2.53 example.com A +time=1 +tries=1

# 查询 IPv6 地址、邮件服务器或反向解析
dig example.com AAAA
dig example.com MX
dig -x 192.0.2.10

# 只显示简短答案
dig @127.0.0.1 example.com A +short

# 沿 DNS 委派层级逐级追踪
dig +trace example.com
```

其中 `@127.0.0.1` 表示把查询直接发给本机回环地址上的 DNS 服务；`+time=1` 将等待时间设为 1 秒，`+tries=1` 限制重试次数，适合快速发现超时。`+trace` 则用于观察从根、顶级域到权威服务器的委派过程，它和“测试某个递归 DNS 能否返回答案”不是同一种测试。

重点看输出中的几部分。下面是结构示意，实际记录、TTL 和耗时会因查询结果而不同：

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR
;; flags: qr rd ra
;; ANSWER SECTION:
example.com.  300  IN  A  192.0.2.10
;; Query time: 2 msec
;; SERVER: 127.0.0.1#53
```

- `status` 是查询状态：`NOERROR` 表示查询过程成功；`NXDOMAIN` 表示域名不存在；`SERVFAIL` 表示服务器未能完成查询；`REFUSED` 表示服务器拒绝服务。`NOERROR` 但没有答案记录时，还要检查查询类型和响应中的其他区段。
- `ANSWER SECTION` 是返回的记录；记录后的数字是 TTL，单位为秒。
- `Query time` 是本机到所选 DNS 服务器这次查询的耗时。如果服务器命中缓存，这个时间不代表它访问权威 DNS 所花的时间。
- `SERVER` 显示实际响应的 DNS 服务器和端口，可用来确认请求是否发到了预期的 dnsmasq 或上游。
- `flags` 中的 `rd` 表示客户端请求递归查询，`ra` 表示服务器支持递归查询；它们是 DNS 响应标志，不是错误信息。

结合前面的排查场景，可以连续比较：

```bash
# 本机 dnsmasq
dig @127.0.0.1 db.example.com A +time=1 +tries=1

# 已验证可用的上游 DNS
# 替换成实际可用的上游 DNS；将 db.example.com 替换成实际数据库主机名
dig @192.0.2.53 db.example.com A +time=1 +tries=1

# 系统默认 DNS
dig db.example.com A +time=1 +tries=1
```

如果上游查询很快、本机查询超时，优先检查 dnsmasq 的上游设置与转发链路；如果 `dig` 很快但应用仍慢，再检查应用是否使用了其他 DNS 配置，以及系统 hosts/NSS 或应用自身的解析逻辑。`dig` 是 DNS 协议层的测试工具，不会完整模拟所有应用的系统解析流程。

## 八、为什么 dnsmasq 配错会让接口慢几秒

应用访问数据库时，如果数据库地址写的是主机名，PHP 等程序通常要先把主机名解析成 IP，再建立数据库连接。因此，即使数据库和 SQL 本身很快，DNS 查询卡住也会拖慢整个接口。

一个典型问题是解析链路形成自我转发：

```text
系统把请求交给 127.0.0.1
        ↓
本机 dnsmasq 收到请求
        ↓
dnsmasq 又把请求转发回 127.0.0.1
```

如果 `127.0.0.1` 恰好仍指向同一个 dnsmasq，就可能出现循环或超时。另一个常见问题是 dnsmasq 的上游 DNS 不可达，或者本机防火墙、网络策略阻断了请求。

可以分层测试，而不是只看数据库端口：

```bash
# 查看系统把 DNS 请求发给谁
cat /etc/resolv.conf

# 测试本机 dnsmasq
dig @127.0.0.1 example.com +time=1 +tries=1

# 绕过 dnsmasq，直接测试一个已知可用的上游 DNS
dig @10.0.0.10 example.com +time=1 +tries=1

# 通过系统解析链路查询
getent hosts example.com
```

示例中的 `10.0.0.10` 要替换为当前网络中已验证可用的上游 DNS 地址。若直接查询上游很快、本机 dnsmasq 查询超时，应重点检查 dnsmasq 的监听地址、上游设置和转发链路。

例如，可以明确告诉 dnsmasq 不要从系统 `resolv.conf` 读取上游，并显式配置上游 DNS：

```ini
listen-address=127.0.0.1
interface=lo
bind-interfaces

no-resolv
server=10.0.0.10
server=10.0.0.11
```

配置中的地址需要换成所在网络实际可用的 DNS。`no-resolv` 用于避免 dnsmasq 再从 `resolv.conf` 读取上游；`server=` 则指定转发目标。修改后还要确认配置通过检查、服务已加载新配置，并重新测试完整解析链路。

## 九、排查时的几个提醒

1. **TCP 端口通，不代表域名解析正常。** 如果用 IP 测试数据库连接成功，但应用使用主机名，仍要单独测解析耗时。
2. **`/etc/resolv.conf` 只说明系统配置了哪些解析器。** 它不能单独证明这些解析器工作正常。
3. **容器中的 `127.0.0.1` 通常指容器自身。** 容器网络模式会影响它能否访问宿主机上的 dnsmasq；不要默认容器和宿主机共享回环地址。
4. **监听地址要符合使用范围。** 仅供本机使用时，优先限制在回环地址；供局域网使用时，应只监听可信网卡并配置防火墙，避免把服务暴露成不受控的开放解析器。
5. **由 NetworkManager 等服务管理的解析配置要从对应管理入口修改。** 直接编辑自动生成的文件，可能会在网络重连或重启后被覆盖。

## 总结

DNS 是一套把域名映射到各类网络记录的分布式系统；dnsmasq 是一款常见的轻量级软件，可以在本机或局域网提供 DNS 缓存、转发，并可与 DHCP 等服务配合。

它们的关系可以用一句话概括：

> **DNS 定义“怎么查”，dnsmasq 则可以负责接收、缓存和转发这些查询。**

当接口慢在数据库连接建立之前，别急着只查 SQL。沿着“应用 → 系统解析器 → dnsmasq → 上游 DNS”逐层计时，往往更容易找到真正的等待点。
