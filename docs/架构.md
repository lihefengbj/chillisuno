# 架构与技术选型

## 1. 核心决策：内嵌真实浏览器（而非逆向 API）

Suno 无官方公开 API。对比两条路线后，选择**内嵌 Chromium 浏览器作为运行引擎**：

| 维度 | 直调内部 API | 内嵌浏览器（采用） |
|---|---|---|
| 反风控 | 弱（缺浏览器指纹，易被 Cloudflare 拦截） | 强（真实浏览器环境） |
| 接口变动 | 签名/字段一改即整体失效 | 页面流程稳定，JS 注入跟随官网逻辑 |
| 登录 | 需手动捕获/刷新 cookie | 持久化 Profile，登录态天然保持 |
| 开发 | 前期逆向成本高 | 注入 JS + 拦截响应即可取数 |

具体做法：用 `QWebEngineView` 加载 suno.com，登录态由持久化
`QWebEngineProfile` 保持；业务数据通过页面内 `window.Clerk` 会话令牌
调用 `studio-api.suno.ai`（与官网前端完全同一条链路）。

## 2. 技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.12 | 项目为 IO 密集型；DSP/下载/JSON 生态最强；迭代快 |
| GUI | PySide6 (Qt6) | 原生内嵌 QWebEngine（Chromium），单进程方案 |
| 音频播放 | QMediaPlayer | Qt 原生 |
| 下载 | requests + 队列 | 批量、断点续传 |
| 存储 | SQLite (stdlib) | 曲库缓存、下载记录、归档索引 |
| 音频处理（M4+） | librosa / soundfile / audiomentations / numpy / scipy | 混淆管道 |
| 打包 | PyInstaller | Windows exe / macOS app |

## 3. 为什么不用 C++/Qt6

- 项目为 IO 密集型，无 CPU 密集计算，C++ 性能优势为零
- 后期音频混淆是"改参数 → 试上传 → 再改"的实验循环，Python 迭代速度远优
- DSP 生态（librosa/scipy/audiomentations）底层均为原生代码，性能足够
- 若出现性能热点，用 pybind11 封装 C++ 内核即可，无需整体换语言

## 4. 模块结构

```
chillisuno/
├── main.py                # 入口
├── app/
│   ├── main_window.py     # 主窗口：侧边栏 + 页面栈
│   ├── auth_service.py    # 内嵌浏览器登录窗口、会话管理
│   ├── suno_api.py        # 通过页面 JS 上下文调用 Suno 接口（M2）
│   ├── storage.py         # SQLite 存储（M2）
│   ├── download/          # 下载队列、断点续传（M3）
│   └── audio/             # 音频混淆处理管道（M4）
├── docs/
├── requirements.txt
└── README.md
```

## 5. 数据流

```
用户操作 → Qt UI → AuthService / SunoApi
                    └─ JS 注入 QWebEngine 页面上下文
                        └─ window.Clerk 令牌 → studio-api.suno.ai
下载中心 → 下载队列 → 本地归档目录（SQLite 记录索引）
上传流程 → AudioProcessor 混淆管道 → QWebEngine 上传
```
